# PCIe kernel-internals campaign at v7.2: plan

The plan of the kernel-internals pages on PCIe for an x86-64 host with ACPI, at v7.2: the Campaign block, the page catalog with its clusters, the fences that bind every page, and the batch order.

```yaml kg:campaign
version: v7.2
```

## Execution and verification

The fences below bind every page of the campaign, and every prompt carries them verbatim.

```md kg:bans
(1) no vendor-specific PCIe mechanism or controller behavior documented as the mechanism, and no vendor names, code names or PCI IDs in authored text; concrete usage examples come from the PCI core, the portdrv services and class drivers (NVMe, xHCI, AHCI). Verbatim source excerpts may retain vendor names, code names and PCI IDs. Do not elide or truncate source solely to remove vendor content; (2) no hedging wordings ([style.hedges]); (3) no devicetree-based platform named and no OF path or non-x86 architecture documented as the mechanism: the x86 ACPI path is the mechanism, other arch glue is named at the seam at most, and a devicetree-only function or attribute may be named once as what x86 does not use; (4) no CXL, SR-IOV, Xen, endpoint-framework, PCI-X, CardBus-as-topic, ROM-access or confidential-computing link-security content; (5) no figure that enumerates a call chain: figures are structural, spatial or temporal ([drawing.triggers]); (6) `struct pcie_device` is never presented as a PCIe device; (7) the term is PCIe unless the topic is specific to conventional PCI.
```

```md kg:mandatory
(1) every PCIe concept named in prose is paired with its kernel representation, the struct, field, constant or function that holds it, in the same paragraph; (2) every helper named gets a fenced, provenance-stamped excerpt and a concrete in-tree usage example in DETAILS; (3) every page enumerates, for the flows it documents, the tracepoints that can fire (usually a verified negative plus the RAS seams), where debug and diagnostic messages print (the pci_dbg, pci_info and pci_err families and the dynamic-debug sites), the asynchronous or deferred hand-offs it crosses, and the debugging surfaces that expose its state (sysfs, procfs, debugfs, the fault-injection and boot parameters), each as an explicit list or an explicit negative; (4) section six is REGISTERS (the subsystem map's entry for `pcie`), drawing the configuration-space registers and fields the page touches; (5) a page that meets `struct pcie_device` states once that it is portdrv's service instance.
```

```md kg:cautions
- (1) Never anchor an excerpt's provenance at the enclosing function's signature line when the shown fragment starts elsewhere; every elision is a marked run, never silent; OTHER SOURCES takes an upstream-thread URL verbatim from a `Link:` or `Closes:` trailer of the commit, never from a hand-built commit URL or a generic specification link; figures are structural, spatial or temporal only.
- (2) The x86 path is one of several: `pci_acpi_scan_root` of arch/x86/pci/acpi.c builds `struct pci_sysdata` and the pci-acpi.c variant serves other architectures; `pci_domain_nr` reads the sysdata; the generic `bus->domain_nr` machinery is compiled out on x86. ```md kg:rules
```

## Batch order

The batch order is a reading path: a reader who has never met PCIe reads the pages in this order and meets each concept after the ones it rests on. Every batch is about five pages and remains the recommended slice, advice to the invoker, never a state machine; a page may cite a later page at the seam.

**Stage 1, configuration space and how an x86 CPU reaches it.** the ECAM load with the regions it addresses and the port-I/O fallback, how x86 chooses between them and what serializes them; then the two capability walks, the PCIe capability accessors that read the offset the walk caches, the MCFG table that describes the regions and the trust checks before a region is mapped; then the two user surfaces that read configuration space.

- B1: device/access/mmio, device/access/port-io, device/access/raw-ops-selection, device/access/locking, acpi/ecam/ecam
- B2: device/cap/capability, device/cap/extended-capability, device/access/pcie-capability-accessors, acpi/ecam/mcfg
